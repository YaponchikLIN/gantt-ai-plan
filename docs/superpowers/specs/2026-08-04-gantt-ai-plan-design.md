# Диаграмма Гантта с AI-редактированием плана — дизайн

Дата: 2026-08-04. Основано на `session_notes.md` (разбор 2026-08-01 — 2026-08-03).

## Что строим

Веб-приложение: диаграмма Гантта, чат для массового редактирования плана
естественным языком, импорт и экспорт Excel. Стек: React, FastAPI, MCP,
модель через OpenRouter.

## Главное правило

> Модель задаёт намерение, код вычисляет следствия.

Модель возвращает операции («сдвинуть задачи 12, 15, 40 на +7»), а не новый
план целиком. Доводы:

1. Переписывая 200 задач ради изменения трёх, даём 197 возможностей ошибиться
   там, где ошибка не требовалась.
2. В плане целиком нельзя отличить намеренное изменение от случайного.
   Сравнение старого и нового — это вычисление диффа, то есть восстановление
   операций, но уже после порчи данных и без информации о намерении.
3. Алгоритм пересчёта нужен в любом случае: у задач есть предшественники,
   сдвиг одной обязан сдвинуть зависимые.
4. Если единица изменения — операция, история пишется сама собой, а откат
   становится обратной операцией.

## Архитектура

Три процесса:

```
plan_mcp_server.py   (процесс 2, stdio)   хранилище, recalculate, инструменты
        ^ MCP
api.py               (процесс 1, uvicorn) 4 эндпоинта, CORS, lifespan
        v HTTP
frontend/            (процесс 3, vite)    GanttChart + Chat
```

MCP-сервер поднимается отдельным процессом через stdio, сессия создаётся один
раз на старте приложения в `lifespan`. Схемы инструментов берутся из
`list_tools()` и конвертируются в формат tools OpenRouter.

План живёт только внутри MCP-сервера — один словарь задач в памяти процесса.
FastAPI своей копии не держит: `GET /api/plan` — это вызов `get_plan` через
MCP. Иначе две правды и рассинхрон.

Разбор Excel (`excel_io.py`) живёт на стороне FastAPI: загрузка файла не
операция агента, модель её не вызывает. Результат парсинга уезжает в
MCP-сервер служебным инструментом `_load_plan`.

## Данные и пересчёт

Задача в хранилище:

```python
{"id": 1, "name": "Разработка", "description": "", "assignee": "Иванов",
 "duration": 10, "predecessors": [2], "not_earlier_than": None}
```

Дат в хранилище нет — они вычисляются. Отдельно хранится `project_start`,
одна на план, приходит из импорта или дефолт «сегодня».

`recalculate()` — три прохода:

1. **Порядок.** Топологическая сортировка (Kahn): задача идёт вперёд, когда
   посчитаны все её предшественники. Осталось нераспределённое → цикл,
   `ValueError` со списком id.
2. **Вперёд.** `start = max(финиши предшественников, not_earlier_than,
   project_start)`, `finish = start + duration`. Конец проекта — максимум
   финишей.
3. **Назад.** `late_finish` считается от конца проекта против стрелок,
   `slack = late_finish − finish`. `slack == 0` → задача на критическом пути.

Возвращает список задач с `start`, `finish`, `slack`, `on_critical_path`.

Обратный проход нужен для `explain_deadline` и для объяснения ситуации
«задача сдвинулась на 5 дней, конец проекта на 2».

**Дни календарные, не рабочие.** Сдвиг на 7 дней — 7 суток, выходные внутри.
Осознанное упрощение: рабочий календарь тянет праздники, регионы и настройку
проекта. Помечается `ponytail:`-комментарием и строкой в roadmap.

**Атомарность.** Каждый мутирующий инструмент делает `deepcopy` хранилища,
правит, зовёт `recalculate()`. Упало — копия возвращается на место, наружу
уходит понятная ошибка. Операция применяется целиком или не применяется
вовсе, иначе одна неудачная фраза оставляет план невычислимым.

## Инструменты

| Инструмент | Аргументы | Назначение |
|---|---|---|
| `get_plan` | — | Прочитать план с вычисленными датами |
| `shift_tasks` | `task_ids`, `days` | Сдвинуть задачи |
| `reassign_tasks` | `task_ids`, `assignee` | Сменить исполнителя, даты не меняются |
| `add_task` | `name`, `duration`, `assignee`, `predecessors` | Добавить задачу |
| `delete_task` | `task_id` | Удалить задачу, перевязать наследников |
| `set_duration` | `task_id`, `duration` | Изменить длительность |
| `add_predecessor` | `task_id`, `predecessor_id` | Добавить зависимость |
| `remove_predecessor` | `task_id`, `predecessor_id` | Убрать зависимость |
| `set_constraint` | `task_id`, `not_earlier_than` | Ограничение «не раньше» |
| `explain_deadline` | `task_id`, `required_finish` | Справка, ничего не меняет |

Плюс служебный `_load_plan(tasks, project_start)` — им пользуется импорт.
Модели он не показывается: `agent_loop` выкидывает из списка инструментов
имена с префиксом `_`.

**Как набор составлен:** прогоном реальных фраз пользователя до конца. Где
сценарий упирается в отсутствие операции — там появляется инструмент.

**Критерий выбора формы инструмента:**

> Что произойдёт, если модель ошибётся или не дотянет?

Отсюда `add_predecessor` / `remove_predecessor` вместо
`set_predecessors(полный список)`: пропущенный элемент в полном списке
означает удаление, то есть молчание модели интерпретируется как команда.
При парных операциях то, что модель не назвала, остаётся на месте. Отсюда же
`shift_tasks` берёт `days`, а не готовую дату.

**Почему нет инструмента «пересчитать»:** пересчёт не выбирается моделью, он
происходит всегда — каждый инструмент заканчивается `return recalculate()`.
Дать модели такой инструмент — значит допустить состояние, где она забыла его
вызвать. Инвариант надёжнее возможности.

**Удаление задачи.** Наследники удаляемой получают её предшественников:
удалили «Разработку» между «Проектированием» и «Тестированием» —
«Тестирование» получает предшественником «Проектирование». Порядок работ
сохраняется, план не съезжает влево. Дубликаты связей после перевязки
схлопываются. Инструмент возвращает список перевязанных связей, чтобы модель
могла сказать пользователю, что именно изменилось. Альтернатива «просто убрать
связи» отвергнута: наследник уезжает на старт проекта, каждая строка формально
верна, а план молча неправильный.

**Ошибки инструментов** возвращаются текстом в `tool_result`, не исключением
процесса: модель должна уметь объяснить пользователю «связь создала бы цикл».
Исключение — невалидные аргументы, их отбивает валидация по схеме до вызова.

## Конфликты и невыполнимые планы

Пользователь просит финиш раньше, чем позволяет цепочка предшественников.
Отказ без объяснения — слабый ответ: пользователю нужно знать, что можно
изменить, а не только что нельзя.

`explain_deadline` ничего не меняет и возвращает готовые числа:

```json
{
  "days_short": 5,
  "fits": false,
  "own_duration": 4,
  "predecessors_chain": [
    {"name": "Разработка",     "duration": 4, "on_critical_path": false},
    {"name": "Документация",   "duration": 7, "on_critical_path": true},
    {"name": "Проектирование", "duration": 5, "on_critical_path": true}
  ]
}
```

Модель складывает из чисел фразу. Считать разницу дат она не должна.

Справка не сообщает, на сколько можно сократить каждую задачу: запас не
свойство отдельной задачи, а результат общего пересчёта. Сократите задачу на
критическом пути слишком сильно — критическим станет другой путь. Проверяется
повторным вызовом справки.

## Агентский цикл

```
messages = история + новая фраза
while шагов < 10:
    ответ = openrouter.chat(messages, tools=схемы_из_mcp)
    если tool_calls: выполнить все, дописать tool-результаты, продолжить
    иначе: вернуть текст
```

Модель — `anthropic/claude-sonnet-4.5` через OpenRouter, имя берётся из
переменной `MODEL`, ключ из `OPENROUTER_API_KEY`. Ключ хранится в `.env`,
`.env` в `.gitignore`.

Потолок 10 итераций. Упёрлись — пользователю уходит «не смог выполнить за
разумное число шагов», а план откатывается: полусделанная последовательность
операций хуже отказа. Снимок делается на входе в `/api/chat` вызовом
`get_plan`, откат — вызовом `_load_plan` с этим снимком. Отдельных служебных
инструментов для отката не заводим: пара уже есть.

Откат по потолку итераций — не то же, что атомарность отдельного инструмента.
Инструмент откатывает свой `deepcopy` внутри MCP-сервера; цикл откатывает всю
последовательность операций одной фразы снаружи.

Системный промпт короткий и про одно: план менять только инструментами, даты
не считать самому, о числах спрашивать `get_plan` и `explain_deadline`.
Границы возможностей всё равно держит набор инструментов, а не текст промпта —
модель физически не может вызвать функцию, которой нет в `tools`.

## HTTP-слой

| Метод | Путь | Сценарий |
|---|---|---|
| GET | `/api/plan` | Страница открылась |
| POST | `/api/import` | Загрузили Excel |
| POST | `/api/chat` | Написали фразу |
| GET | `/api/export` | Выгрузили Excel |

Все возвращают план целиком: после фразы «раскидай задачи Иванова» неизвестно,
сколько задач изменилось, а вычислять на фронте, что именно поменялось, —
снова тот дифф, от которого ушли.

Импорт с ошибками возвращает 422 со списком `{row, column, message}`, а не 500.
500 означает «сервер сломался», 422 — «файл прочитан, данные не годятся, вот
что именно». Фронт по коду решает, показывать список ошибок или писать
«попробуйте позже».

CORS открыт на localhost-порт фронта, иначе браузер заблокирует запросы.

## Excel

Во входном файле предшественники записаны именами, в базе — id. Нужно
соответствие, а один проход не годится: если строка ссылается на задачу ниже
по файлу, её имени в словаре ещё нет, связь теряется. Порядок строк
произволен.

Два прохода: сначала раздать id и заполнить словарь имён, затем пройти те же
строки заново — теперь любое имя находится.

Требования к ошибкам импорта:

- указывают на строку и колонку: не «файл не соответствует шаблону», а
  «строка 7, колонка предшественники: задача „Проктирование“ не найдена»;
- собираются все сразу, а не по одной за загрузку;
- файл отклоняется целиком. Частичная загрузка не ломает расчёты, а даёт
  молча неверный ответ.
session_notes.md` и
**Цикл ловится при импорте, а не при пересчёте:**

> Ошибку ловят там, где есть контекст для внятного сообщения.

В `parse_excel` известны имена и номера строк. В `recalculate` только id, и
пользователь получил бы «Цикл в зависимостях: [1, 2, 3]». Логика не пишется
заново: `_check_cycles` — это `recalculate` с вырезанной арифметикой дат.

Экспорт пишет предшественников именами, а не id: основной сценарий —
выгрузил, поправил руками в Excel, загрузил обратно.

## Фронт

Vite + React, JavaScript, без TypeScript и без UI-библиотеки. Состояние — три
`useState` в `App.jsx`: `plan`, `messages`, `loading`. Источник правды один —
ответ сервера, любой запрос заменяет `plan` целиком.

| Компонент | Что делает |
|---|---|
| `App.jsx` | Состояние, вызовы API, раскладка |
| `GanttChart.jsx` | SVG: шкала дней, полоски, стрелки, модалка по клику |
| `Chat.jsx` | Лента сообщений, поле ввода, блокировка на время ответа |
| `Toolbar.jsx` | Импорт, экспорт, показ ошибок 422 списком |

Бэкенд хранит длительности и связи, наружу отдаёт посчитанные `start` и
`finish`. React ничего не вычисляет — переводит даты в координаты:

```
x = LABEL_WIDTH + daysBetween(начало_шкалы, дата) * DAY_WIDTH
ширина полоски = daysBetween(start, finish) * DAY_WIDTH
```

Вход компонента задачи: `name`, `start`, `finish`, `assignee`, `duration`,
`description`, `predecessors`, `slack`, `on_critical_path`. Критический путь
красится отдельным цветом, запас показывается в модалке.

Стрелки нужны, потому что позиции полосок показывают результат, а стрелки —
причину: без них сдвиг соседней задачи выглядит необъяснимым скачком.
Отсутствие исходящей стрелки означает «задача никого не ждёт», но не значит,
что её никто не ждёт.

Стрелка — `<path>` с ломаной, два маршрута. Есть горизонтальный зазор между
финишем предшественника и стартом наследника — идём вправо, вниз, вправо.
Зазора нет (предшественник кончается ровно в день старта) — обходим снизу,
иначе линия идёт вправо и возвращается назад, а наконечник смотрит не туда.

Чат отправляет `POST /api/chat`, получает текст модели и новый план,
перерисовывает целиком. Оптимистичных обновлений нет: пока модель не
ответила — спиннер и блокировка ввода, потому что результат фразы предсказать
нельзя. Ошибки бэкенда показываются в ленте отдельным стилем.

Правила оформления диаграммы (палитра, оси, светлая и тёмная тема) берутся из
скила `dataviz` на этапе реализации.

## Проверка

1. **`test_plan.py`** — обычные `assert`, запускается через `pytest` и как
   `python test_plan.py`. Покрывает:
   - три задачи с цепочкой предшественников дают шесть вычисленных дат;
   - опоздание на 5 дней при запасе 3 двигает конец проекта на 2, критический
     путь переезжает с одной ветки на другую;
   - цикл ловится и в `parse_excel`, и в `recalculate`;
   - неудачный `add_predecessor` оставляет план ровно как был;
   - `delete_task` перевязывает наследников, конец проекта не уезжает влево;
   - круг «экспорт → импорт» даёт тот же план.
2. **`demo_scenarios.py`** — прогон инструментов без модели: детерминированно
   и не тратит запросы к API.
3. **Живой прогон** — оба процесса подняты, браузер открыт, стрелки и чат
   проверяются глазами. Дефект отрисовки стрелок тестом не ловится.

Фронт тестами не покрывается: вычислений там нет, только перевод чисел в
координаты.
