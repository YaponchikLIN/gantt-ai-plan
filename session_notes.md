# Конспект сессии: тестовое задание full-stack AI-native

Разобрано за 2026-08-01 — 2026-08-03. Проект: диаграмма Гантта + чат для
массового редактирования плана + импорт/экспорт Excel. Стек: React, FastAPI,
MCP, LLM через API.

---

## 1. Контракт между чатом и планом

**Вопрос:** пользователь пишет «перенеси все задачи Иванова на неделю вправо»,
в плане 200 задач. Что возвращает модель?

**Развилка:**
- Вариант А — модель возвращает весь новый план (200 задач с новыми датами).
- Вариант Б — модель возвращает операции («сдвинуть задачи 12, 15, 40 на +7»),
  даты пересчитывает код.

**Выбран Б. Доводы:**

1. Галлюцинация — не «модель врёт», а свойство генерации: каждый следующий
   токен порождается по вероятности. Чем длиннее выход, который надо
   воспроизвести дословно, тем выше шанс отклонения. Переписывая 200 задач
   ради изменения трёх, даём 197 возможностей ошибиться там, где ошибка
   не требовалась.
2. В варианте А нельзя отличить намеренное изменение от случайного. Попытка
   отличить через сравнение старого и нового плана — это и есть вычисление
   диффа, то есть восстановление варианта Б, но уже после порчи данных
   и без информации о намерении.
3. Алгоритм пересчёта нужен в обоих вариантах: у задач есть предшественники,
   сдвиг одной обязан сдвинуть зависимые.
4. Побочная выгода: если единица изменения — операция, история пишется сама
   собой, а откат становится обратной операцией.

**Главное правило проекта:**

> Модель задаёт намерение, код вычисляет следствия.

## 2. Tool calling: что происходит внутри

**Термины:**

- **Tool calling** — режим, в котором вы описываете модели набор функций: имя,
  назначение, JSON-схема аргументов. Модель не выполняет функцию, а возвращает
  её имя и аргументы. Выполняет ваш код.
- **Tool call** — структура, которую модель возвращает: `{name, input}`.
- **MCP (Model Context Protocol)** — стандартный протокол описания и вызова
  инструментов, вынесенный в отдельный сервер. Инструменты становятся
  переиспользуемыми и подключаемыми к разным клиентам.

**Полная цепочка одного сообщения:**

```
фраза пользователя
  -> бэк отправляет модели: messages + tools
  -> модель возвращает блок tool_use {name, input}
  -> бэк валидирует аргументы по схеме
  -> бэк вызывает инструмент на MCP-сервере
  -> ИНСТРУМЕНТ МЕНЯЕТ БАЗУ И ПЕРЕСЧИТЫВАЕТ ДАТЫ
  -> результат кладётся в messages как tool_result (роль user)
  -> модель вызывается снова: либо ещё tool_use, либо текст
  -> фронт получает новый план и перерисовывает
```

**Частые ошибки в формулировках (проверять на защите):**

| Неверно | Верно |
|---|---|
| MCP передаёт аргументы в функции | MCP описывает инструменты и доставляет вызов; выбирает модель, выполняет код |
| Модель отправляет результат в Python | Модель возвращает блок; код сам его забирает. Инициатива всегда на стороне кода |
| Список функций пишем в системном промпте | Список идёт отдельным полем `tools` — есть валидация схемы и типизированный ответ вместо парсинга текста |
| База правится после ответа модели | База правится внутри инструмента, до возврата результата модели |

**Следствие:** модель физически не может вызвать функцию, которой нет
в `tools`. Границы возможностей агента задаются набором инструментов,
а не строгостью промпта.

**Агентский цикл** — то, что отличает агента от одиночного запроса. Пример:
«Иванов заболел, сдвинь всё его на три дня» при отсутствии инструмента поиска
по исполнителю → модель вызывает `get_plan`, находит задачи Иванова сама,
затем вызывает `shift_tasks`. Два вызова, между ними работает код.

## 3. Даты: почему их нет в базе

Формат входного Excel: задача, описание, исполнитель, **длительность**,
предшественники. Дат в исходных данных нет.

**Предшественник** — задача, которая должна закончиться до старта данной.

**Формула пересчёта:**

```
старт  = max(финиш предшественников, ограничение «не раньше», старт проекта) + сдвиг
финиш  = старт + длительность
```

Обход топологический: задача считается, только когда посчитаны все её
предшественники.

**Пример на трёх задачах** (старт проекта 1 сентября):

| задача | длит. | предш. | старт | финиш |
|---|---|---|---|---|
| Проектирование | 5 | — | 01.09 | 06.09 |
| Разработка | 10 | Проектирование | 06.09 | 16.09 |
| Тестирование | 4 | Разработка | 16.09 | 20.09 |

Ни одна дата не хранилась — все шесть вычислены.

**Следствие для аргументов инструментов:** в аргументы попадает только то, что
нельзя вывести из данных. Исполнитель, длительность предшественника, даты — не
попадают. Календарная дата из фразы пользователя — попадает, её больше
неоткуда взять.

**Ограничение** — поле «не раньше такой-то даты». Единственное место, где дата
приходит извне.

## 4. Критический путь

**Запас** — промежуток, на который задача может опоздать, ничего не сдвинув.

**Критический путь** — цепочка задач, где ни у одной нет запаса. Только её
сокращение двигает конец проекта.

**Пример.** Проектирование (01.09–06.09) → две параллельные ветки: Разработка
(4 дня, 06.09–10.09) и Документация (7 дней, 06.09–13.09) → Тестирование
ждёт обеих, стартует 13.09.

- Сократить Разработку — бесполезно, Тестирование всё равно ждёт Документацию.
  У Разработки запас 3 дня.
- Сократить Документацию на 3 дня — конец проекта уедет на 3 дня влево.
- Разработка опаздывает на 5 дней при запасе 3 → конец проекта уезжает на 2.
  Три дня съел запас.

**Критический путь непостоянен:** после каждого изменения пересчитывается.
В примере выше после опоздания Разработки критический путь переехал с
Документации на Разработку, хотя связи не менялись.

## 5. Набор инструментов

**Метод составления:** прогонять реальные фразы пользователя до конца.
Где сценарий упирается в отсутствие операции — там появляется инструмент.
Это же и есть ответ на защите на вопрос «почему инструменты именно такие».

**Итоговый набор:**

| Инструмент | Аргументы | Назначение |
|---|---|---|
| `get_plan` | — | Прочитать план с вычисленными датами |
| `shift_tasks` | `task_ids`, `days` | Сдвинуть задачи |
| `reassign_tasks` | `task_ids`, `assignee` | Сменить исполнителя (даты не меняются) |
| `add_task` | `name`, `duration`, `assignee`, `predecessors` | Добавить задачу |
| `set_duration` | `task_id`, `duration` | Изменить длительность |
| `add_predecessor` | `task_id`, `predecessor_id` | Добавить зависимость |
| `remove_predecessor` | `task_id`, `predecessor_id` | Убрать зависимость |
| `set_constraint` | `task_id`, `not_earlier_than` | Ограничение по дате |
| `explain_deadline` | `task_id`, `required_finish` | Справка: ничего не меняет |

**Не сделано, но названо:** удаление задачи. Нетривиально из-за наследников —
что делать с теми, кто на неё ссылался.

**Развилка «полный список против пары add/remove»:**

`set_predecessors(task, [полный новый список])` покрывает все сценарии, потому
что принимает итоговое состояние. Но цена ошибки высокая: пропущенный элемент
означает удаление, то есть молчание модели интерпретируется как команда.
У `add_predecessor` / `remove_predecessor` то, что модель не назвала, остаётся
на месте. Ошибка в первом случае разрушает данные, во втором не делает ничего.

**Общий критерий выбора инструмента:**

> Что произойдёт, если модель ошибётся или не дотянет?

Отсюда же: `shift_tasks` берёт `days`, а не готовую дату.

**Почему нет инструмента «пересчитать»:** пересчёт не выбирается моделью, он
происходит всегда — каждый инструмент заканчивается `return recalculate()`.
Дать модели такой инструмент — значит допустить состояние, где она забыла его
вызвать. Инвариант надёжнее возможности.

## 6. Конфликты и невыполнимые планы

**Ситуация:** «Тестирование должно закончиться до 12 сентября», но цепочка
предшественников этого не позволяет.

**Почему «отказать и ничего не менять» — слабый ответ:** пользователю нужно
знать, что можно изменить, а не только что нельзя.

**Решение:** справочный инструмент `explain_deadline`. Ничего не меняет,
возвращает:

```json
{
  "days_short": 5,
  "fits": false,
  "own_duration": 4,
  "predecessors_chain": [
    {"name": "Разработка",     "duration": 4, "on_critical_path": false},
    {"name": "Документация",   "duration": 7, "on_critical_path": true},
    {"name": "Проектирование", "duration": 5, "on_critical_path": true}
  ]
}
```

Модель получает готовые числа и складывает из них фразу. Считать разницу дат
она не должна — это работа кода.

**Почему в справке нет «на сколько можно сократить каждую задачу»:** запас не
свойство отдельной задачи, а результат общего пересчёта. Сократите задачу
на критическом пути слишком сильно — критическим станет другой путь.
Проверяется повторным вызовом справки.

**Атомарность.** Попытка замкнуть цикл через `add_predecessor` откатывается:
связь добавляется, пересчёт падает, связь удаляется, наружу уходит понятная
ошибка. Операция применяется целиком или не применяется вовсе — иначе одна
неудачная фраза оставляет план невычислимым.

## 7. Импорт и экспорт Excel

**Проблема:** в файле предшественники записаны именами («Проектирование»),
в базе — id (`[1]`). Нужно соответствие.

**Словарь имён** — `dict`, где ключ имя задачи из файла, значение присвоенный id.

**Почему один проход не годится:** если строка ссылается на задачу, которая
идёт в файле ниже, её имени в словаре ещё нет — связь теряется. Порядок строк
в Excel произволен.

**Решение — два прохода:**
1. Раздать id, заполнить словарь имён. Связи не трогаем.
2. Пройти те же строки заново, теперь любое имя находится.

**Почему нельзя молча удалить ненайденную связь:** план будет выглядеть
нормально, но окажется неверным, и пользователь об этом не узнает. Тихая
неправильность хуже падения.

**Требования к ошибкам импорта:**
- указывают на строку и колонку: не «файл не соответствует шаблону», а
  «строка 7, колонка предшественники: задача «Проктирование» не найдена»;
- собираются все сразу, а не по одной за загрузку;
- файл отклоняется целиком. Довод: частичная загрузка не ломает расчёты,
  а даёт молча неверный ответ.

**Цикл в зависимостях** — задачи ссылаются друг на друга по кругу
(A ждёт B, B ждёт C, C ждёт A). Ни одна не может начаться, дат не существует.
Каждая строка при этом корректна, опечаток нет.

**Где ловить цикл:** при импорте, не при пересчёте.

> Ошибку ловят там, где есть контекст для внятного сообщения.

В `parse_excel` известны имена и номера строк. В `recalculate` только id —
пользователь получил бы «Цикл в зависимостях: [1, 2, 3]».

Логику писать заново не нужно: `_check_cycles` — это `recalculate`
с вырезанной арифметикой дат.

**Экспорт** пишет предшественников именами, а не id. Причина — круговой
сценарий: выгрузил → поправил руками в Excel → загрузил обратно. В ТЗ он
назван как основной сценарий для демо-видео.

## 8. Диаграмма Гантта

**Граница фронта и бэка:** бэкенд хранит длительности и связи, наружу отдаёт
уже посчитанные `start` и `finish`. React ничего не вычисляет — переводит даты
в координаты.

**Перевод даты в пиксели:**

```
x = LABEL_WIDTH + daysBetween(начало_шкалы, дата) * DAY_WIDTH
ширина полоски = daysBetween(start, finish) * DAY_WIDTH
```

**Вход компонента:** `name`, `start`, `finish`, `assignee`, `duration`,
`description`, `predecessors`.

**Зачем стрелки, если позиции полосок и так всё показывают:** позиции
показывают результат, стрелки — причину. Без стрелок сдвиг соседней задачи
выглядит как необъяснимый скачок.

**Что означает отсутствие стрелки:** задача никого не ждёт. Но не означает,
что её никто не ждёт — входящих стрелок нет и у первой задачи цепочки,
от которой зависят все остальные.

**Косвенные связи.** Разработка и Документация не связаны напрямую, но обе
ведут в Тестирование и потому влияют друг на друга через запас. Стрелки
показывают прямые связи, последствия расходятся дальше.

**Дефект отрисовки, который пришлось чинить:** когда предшественник кончается
ровно в день старта наследника, горизонтального зазора нет, линия идёт вправо
и возвращается назад — наконечник смотрит не туда. Маршрут разведён на два
случая: с зазором и без.

## 9. Склейка: FastAPI

Четыре сценария ТЗ — четыре эндпоинта:

| Метод | Путь | Сценарий |
|---|---|---|
| GET | `/api/plan` | Страница открылась |
| POST | `/api/import` | Загрузили Excel |
| POST | `/api/chat` | Написали фразу |
| GET | `/api/export` | Выгрузили Excel |

**Почему все возвращают план целиком:** после фразы «раскидай задачи Иванова»
неизвестно, сколько задач изменилось. Вычислять на фронте, что именно
поменялось, — это снова тот дифф, от которого ушли в разделе 1.

**Коды ответов:** импорт с ошибками возвращает 422 со списком, а не 500.
500 означает «сервер сломался», 422 — «файл прочитан, данные не годятся,
вот что именно». Фронт по коду решает, показывать ошибки или писать
«попробуйте позже».

**CORS** нужен, потому что фронт живёт на другом порту, и браузер иначе
заблокирует запросы. `middleware` — прослойка, через которую проходит каждый
запрос (логирование, авторизация, CORS); связывает фронт с бэком не она,
а сами эндпоинты.

**MCP-сессия** поднимается один раз на старте приложения через `lifespan`,
а не на каждый запрос: это отдельный процесс.

## 10. Сознательный техдолг → Roadmap to production

1. **План в памяти процесса.** Общий для всех пользователей, теряется при
   перезапуске. Нужна БД и разделение по пользователям.
2. **История диалога одна на приложение.** Модель между вызовами ничего не
   помнит, история передаётся заново каждый раз. При двух пользователях фразы
   попадают в одну ленту: первый пишет «перенеси задачи Иванова на неделю»,
   второй «а теперь на Петрова» — модель считает это одним разговором.
   Ошибки не возникнет, план поменяется не так, как хотел никто.
3. **Нет блокировки на план.** Параллельные правки накладываются.
4. **Нет авторизации.**
5. **Нет удаления задач.**
6. **CORS открыт на localhost**, в продакшене нужен закрытый список.

Формулировка для документа: что сделано упрощённо, чем это грозит, что
потребуется для боевого состояния, в каком порядке закрывать.
