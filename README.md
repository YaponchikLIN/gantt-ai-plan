# Диаграмма Гантта с редактированием через чат

**Развёрнутое приложение: https://gantt-ai-plan.onrender.com** — бесплатный тариф Render, сервис
засыпает после 15 минут простоя, первый запрос после сна идёт около полуминуты.

Диаграмма Гантта, которую редактируют фразой на естественном языке. Пользователь пишет «перенеси
задачи Петрова на неделю» или «удали интеграцию», и план перестраивается: даты, запас и критический
путь пересчитываются заново. Три процесса: MCP-сервер хранит план и выдаёт одиннадцать инструментов,
FastAPI-бэкенд ведёт цикл обращений к модели поверх одной долгоживущей MCP-сессии, React-фронтенд
переводит вычисленные даты в координаты SVG.

## Главное правило

Модель формулирует намерение, код считает последствия. Модель никогда не возвращает новый план — она
вызывает инструменты («сдвинь задачи 12, 15, 40 на +7»), а даты пересчитывает код. Если бы модель
переписывала двести задач ради правки трёх, у неё было бы сто девяносто семь шансов ошибиться там, где
ошибка была не нужна.

## Запуск

Ключ OpenRouter нужен только для чата. Диаграмма, импорт и экспорт работают и без него.

### Через Docker — одна команда

```bash
docker build -t gantt-ai-plan .
docker run --rm -p 8080:8080 -e OPENROUTER_API_KEY=sk-or-v1-... gantt-ai-plan
```

Открыть http://localhost:8080. Python и Node на машине не нужны: в контейнере и бэкенд, и собранный
фронтенд, и MCP-сервер.

### Из исходников

Нужны Python 3.11+ и Node 20+.

```bash
python3 -m venv .venv
.venv/bin/pip install -r backend/requirements.txt
npm install --prefix frontend
cp backend/.env.example backend/.env   # вписать ключ OpenRouter
```

Два процесса, в разных терминалах:

```bash
cd backend && ../.venv/bin/python -m uvicorn api:app   # бэкенд на 8000
npm run dev --prefix frontend                          # фронтенд на 5173
```

Открыть http://localhost:5173.

Если порт 8000 занят, фронтенд читает адрес бэкенда из `VITE_API_BASE`:

```bash
cd backend && ../.venv/bin/python -m uvicorn api:app --port 8010
VITE_API_BASE=http://localhost:8010/api npm run dev --prefix frontend
```

При старте бэкенд заполняет план тестовыми данными из `backend/sample_data.py` — десять задач с
ветвлением и видимым критическим путём, старт проекта сегодняшний. Открытая страница сразу показывает
диаграмму, загружать файл для этого не нужно. Загрузка Excel заменяет план целиком.

## Файлы Excel для проверки

- `sample_plan.xlsx` — образец формата: те же десять задач, что подставляются при старте.
- `demo_plan.xlsx` — другой проект на одиннадцать задач. Нужен именно другим: загрузка плана,
  совпадающего с засидированным, ничего не меняет на экране, и проверить импорт по картинке нельзя.

Оба пересобираются из `backend/sample_data.py` командой `python demo_scenarios.py --sample`.

```bash
cd backend && ../.venv/bin/python -m pytest test_plan.py -q
```

70 тестов.

```bash
cd backend && ../.venv/bin/python demo_scenarios.py
```

Прогоняет весь набор инструментов без обращения к модели — детерминированно и без затрат на запросы.

У фронтенда тестов нет: он не производит вычислений, только переводит уже посчитанные даты в
координаты SVG. Диаграмма проверялась иначе — рендерингом разметки и сверкой геометрии.

## Как это устроено

Три процесса: MCP-сервер (`backend/plan_mcp_server.py`) хранит план и одиннадцать инструментов, FastAPI
(`backend/api.py`) ведёт цикл модели поверх одной MCP-сессии, React (`frontend/src`) рисует SVG.
Даты нигде не хранятся: хранятся длительности, зависимости и ограничения, а `recalculate()` каждый раз
считает их заново прямым и обратным проходом по графу задач — прямой проход даёт старт и финиш, обратный
даёт поздний финиш, из которого выводится запас и критический путь (`slack == 0`).

Набор инструментов не придуман заранее — он собран прогоном реальных фраз до конца, и форма аргумента
каждого инструмента выбрана вопросом «что будет, если модель ошибётся». Поэтому `add_predecessor`
добавляет одну зависимость, а не принимает полный список — ошибочный вызов не стирает остальные связи.
Поэтому `shift_tasks` принимает `days`, а не целевую дату — сдвиг на N дней от текущего старта не может
случайно телепортировать задачу в прошлое, если модель перепутала месяц.

## Что показал живой прогон

**«Перенеси задачи Петрова на неделю вправо»** — модель вызвала `get_plan`, сама нашла в нём три
задачи Петрова, затем вызвала `shift_tasks`. Все три задачи сдвинулись ровно на семь дней, и конец
проекта сдвинулся вместе с ними. Инструмента «сдвинуть по исполнителю» не существует — это цикл агента
сделал два шага с кодом между ними: один вызов вернул план, второй его изменил.

**«Приёмка должна закончиться до 10 сентября. Успеваем?»** — ответ «не хватает 5 дней» со списком
критической цепочки, план не изменился. Арифметика неочевидна: финиш — 16 сентября, пользователь
назвал 10-е, но ответ — пять дней, а не шесть. На момент этого прогона `explain_deadline` требовал от
модели самой сдвигать дату на день вперёд («к 10-му включительно» → передать 11-е), и модель сделала
это верно. Но перекладывать на модель арифметику дат — риск: ошибка в сдвиге молча меняет `fits` и
`days_short`, а пользователь услышит уверенный неверный ответ. Поэтому после этого прогона граница
была перенесена в код: инструмент принимает дату пользователя как есть (`required_finish="2026-09-10"`)
и сам прибавляет день по флагу `inclusive` (по умолчанию `True`).

**«Удали Интеграцию»** — её наследники унаследовали её предшественников и остались на 30 августа,
вместо того чтобы съехать назад к началу проекта. Это и есть смысл `delete_task`: удаление задачи не
рвёт граф, а перевязывает его.

## Дедлайн проекта

`set_deadline` сохраняет дату, к концу которой работа должна закончиться. Дедлайн ничего не запрещает:
удлинить задачу или сдвинуть сроки он не мешает — планировщик, который не даёт ухудшить план,
бесполезен. Его дело в том, чтобы последствие было видно сразу. Каждый ответ плана несёт
`fits_deadline` и `days_late`, а шапка показывает «в срок» или красное «опоздание на N дней».

## Использование AI-ассистентов

Дизайн прорабатывался в диалоге с моделью и записан в `docs/superpowers/specs/`.
Реализация шла по письменному плану, задача за задачей, сначала тесты, потом
код. Каждая задача проверялась дважды: сначала на соответствие спецификации, потом на качество кода. Эти
проверки нашли настоящие дефекты в коде, написанном по тому же плану — например:

- **`shift_tasks` считал сдвиг от устаревшего ограничения, а не от текущего старта.** Если задачу
  держали предшественники, инструмент записывал новое ограничение, ничего не сдвигал и отчитывался об
  успехе. Теперь база сдвига — текущий старт, он уже учитывает и предшественников, и прежнее ограничение.
- **Агентский цикл прятал служебные инструменты из списка, но выполнял любое имя, которое вернёт
  модель.** То есть `_load_plan`, заменяющий план целиком, был достижим галлюцинированным вызовом.
  Теперь имя проверяется по белому списку тех же схем, что ушли модели: спрятать не значит запретить.
- **`/api/chat` откатывал план только при исчерпании лимита шагов.** Если модель падала посреди цепочки
  вызовов, план оставался наполовину изменённым, а фраза навсегда оседала в истории диалога. Теперь
  откат и очистка истории происходят на любом отказе.

## Деплой

Один контейнер: FastAPI отдаёт собранный фронтенд как статику с того же origin (`/api/...` без CORS),
MCP-сервер по-прежнему поднимается подпроцессом внутри контейнера.

### Локально, через Docker

```bash
docker build -t gantt-ai-plan .
docker run --rm -d -p 8080:8080 --name gantt-ai-plan gantt-ai-plan
curl -s localhost:8080/api/plan   # десять задач из sample_data.py
curl -s localhost:8080/          # index.html
docker stop gantt-ai-plan
```

Ключ OpenRouter в контейнер не нужен для этой проверки: `/api/chat` без ключа не дергаем.
`backend/.env` в образ не копируется (см. `.dockerignore`) — ключ туда никогда не попадает.

Порт берётся из переменной `PORT`, если она задана площадкой, иначе 8080.

### Render

`render.yaml` — готовый Blueprint: тип `web`, сборка из `Dockerfile`, бесплатный тариф, health check
на `/api/plan`. Развёртывание:

1. New → Blueprint в дашборде Render, выбрать этот репозиторий. Render прочитает `render.yaml`.
2. Он спросит значение `OPENROUTER_API_KEY` — в файле стоит `sync: false`, поэтому ключ хранится только
   в дашборде и в репозиторий не попадает.
3. Deploy. Первая сборка занимает несколько минут.

На бесплатном тарифе сервис засыпает после 15 минут без запросов и просыпается за полминуты.

### Что нужно знать про хостинг

План и история диалога живут в памяти одного процесса (см. `docs/ROADMAP.md`, пункты 1 и 2). Перезапуск
контейнера или пробуждение после сна возвращают план к тестовым данным из `sample_data.py`. Для демо это
ожидаемо и стоит первым пунктом роадмапа — не дефект, который следует чинить здесь.

Образ ни к чему не привязан: это обычный `Dockerfile`, слушающий порт из переменной `PORT`. Любая
площадка с поддержкой контейнеров или собственная виртуальная машина подойдут без правок.
